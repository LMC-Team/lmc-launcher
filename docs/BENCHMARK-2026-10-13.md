## 三、结论

### 1. lmc 性能层对帧率是**中性**的(既不加分也不扣分)

同一 APK 下,lmc 开(84/86)与 lmc 关(77/85)在测量噪声(±5 fps)内无法区分。
绑大核、温度监控线程、音频初始化这些本身开销极小;而**曾经"把 GC/JIT 线程迁到小核"
的策略经实测撤销**(见结论 3)——修正后的性能层不再有负面作用。

### 2. 集成版整体比原版慢 ~11%(85 vs 96 fps),**与 lmc 无关**

lmc 开/关都在 81-86 区间,而原版两轮 97/95 高度一致。差距来自**上游 2.7 相对 2.6.1
的变化**(两版启动器在游戏进程内设置的某些环境/组件存在差异,未逐项定位)。
注意对照不是完全同版:原版是 2.6.1,我们是 2.7——这是本轮对比最主要的局限。

### 3. 本轮发现并修复了 lmc 两个真实缺陷

| 缺陷 | 实锤证据 | 修复 |
|---|---|---|
| JIT 参数注入位置错误 | MC 日志:`Completely ignored arguments: [-XX:CICompilerCount=4, ...]` —— 参数落在主类之后,JVM 根本没收到 | 移到 `launchArgs`(含 -cp/主类)拼入**之前**,现已在 JVM 选项区生效 |
| GC/JIT 线程迁小核有害 | G1 的 STW 停顿由并行 GC 线程执行,放在 A55 小核上停顿显著变长 | 只迁移纯后台线程(VM Periodic Task / Service Thread / Common-Cleaner / Notification Thread),GC/JIT 线程交还调度器 |

### 4. 温度是这台设备上最大的性能变量

每次运行内温度从 45°C 升到 ~67°C,样本间波动 ±8 fps;任何"小优化"的收益都会被
热噪声淹没。**要在这台机器上获得可感知的提升,方向应该是降低发热**(渲染分辨率/
帧率上限/亮度),而不是 CPU 调度微优化。

---

## 四、局限与改进方向

1. **上游版本不同**(2.6.1 vs 2.7)是本轮无法消除的变量;若要精确归因,需构建
   "2.7 无 lmc"的纯上游对照。
2. 单设备、单世界、每轮 50s 采样窗口,样本噪声 ±5-8 fps;结论只支持"量级判断"。
3. 未测:世界生成耗时、区块加载速度、内存峰值(内存上 lmc 版略高 ~0.1-0.2G,
   主要来自 lmc core 的 native 库与状态)。
4. 建议后续:把 Krypton 渲染器的版本在两边对齐后重测;以及用 **MC F3 + 固定视角
   长采样** 代替 overlay 读数以降噪。

### 6.3 本轮新发现的工程问题

| 问题 | 实测证据 | 建议 |
|---|---|---|
| 大核判定阈值在 SD870 上失效 | 870 中核 2.419GHz / 超大核 3.187GHz = 75.9% < 80% 阈值 → 中核三颗被判小核,**游戏主线程只绑 [7] 单核**;vivo 上比值 96% 无此问题 | 改用 `cpu_capacity`(该设备实测 313/777/777/1024,清晰三档),频率阈值仅作回落 |
| zl2 对 fabric 库的解析要求 | 自造 `{name,url}` 库条目 → zl2 解析崩溃(IndexOutOfBounds);缺 `downloads.artifact`(path/sha1/size)→ KnotClient 找不到(classpath 缺失) | 自包含 fabric 版本必须给**完整标准 maven 格式**;且 zl2 对部分库按 `<组尾段>-<artifact>.jar` 命名查找(如 `fabricmc-fabric-loader.jar`) |
| MIUI 测试环境差异 | uiautomator 在游戏画面返回 null root;安装需人工确认;adb 无法强制刷新率 | 采样改用截图读数;装机需人工配合 |
| MC 的 session.lock 时序 | session.lock 在世界**开始加载**时即写入,不代表已进世界 | 稳定期需 ≥75s(FO 首次加载更慢) |


## 七、帧锁解除后的复测(2026-10-14 上午,Poco F3)

### 7.1 30fps 之谜的真凶:MC 1.21.2+ 闲置降帧(inactivityFpsLimit)

**勘误**:§6.2 的"MIUI 锁 60Hz 半速率"结论**错误**,向柠枺致歉——

- MC 1.21.2 新增 `inactivityFpsLimit`(闲置降帧),合法值只有
  `"minimized"`(仅最小化时)与 `"afk"`(挂机 30s 后锁 30fps,**默认**)
- 我们部署的 options.txt 写了非法值 `off` → MC **静默回退默认 afk**
  → 每轮采样都在静置期 → 三方一致 30 fps
- 柠枺在视频设置里把该项调为"最小化时"(MC 写回 `"minimized"`)后解除;
  另一个启动器里残留的未带引号 `off` 依旧回退 afk → 原版那轮仍锁 30
- 正确配置:`inactivityFpsLimit:"minimized"`(必须带引号)
- vivo 那轮(MC 1.21.1)没有此选项,所以从未触发——这也是两台设备
  "表现矛盾"的原因

**森林景(真实 GPU 负载)热态下 lmc 开全面崩塌**。

### 7.3 重大发现:lmc 绑核在 SM8250 热态下导致帧率崩塌(130 倍)

**双臂对照实验**(同设备/同 APK/同世界/同热态 61.9°C,仅切换 lmc):

| 臂 | lmc | FPS | CPU 时钟快照 |
|---|---|---|---|
| 1 | 开 | **1** | cpu7=1.40GHz(上限 3.19),中核 1.48 |
| 2 | 关 | **130** | 中核+cpu7 均 1.05GHz |

**机制**(证据链完整):

1. 旧大核判定用"频率 ≥ 最高簇 80%"阈值,SM8250 中核 2.419/超大核
   3.187 = 75.9% < 80% → **中核三颗 A77 被判小核**
2. 游戏主线程被绑死在 **[7] 单核**(日志实锤 `游戏主线程 -> 大核 [7]`)
3. 热节流时超大核降频最狠且线程**无法迁移**;lmc 关闭时调度器可把
   游戏线程撒到中核/超大核全部 4 颗性能核
4. 冷态下绑定无此问题(A2 611 vs B2 583,甚至略快)——**坑只在热态**

**修复**(已提交):

- `core/src/sched/cpu_topology.cpp`:大核判定改为 **cpu_capacity 优先**
  (ARM 标准节点,两台真机实测 313/777/1024,清晰三档),规则 = "最低簇
  为小核,其余全部为大核",废除相对阈值;容量不可读回退频率(同一规则)
- `core/src/sched/thread_affinity.cpp`:新增防呆护栏——**大核簇 < 2 颗时
  拒绝绑核**(真实 SoC 性能簇至少 2 颗,单核 = 误判)
- 修复后 870 上:游戏主线程绑 [4,5,6,7],热态下调度器有完整逃逸空间

**修复验证**(同款热态场景,65.4°C,lmc 开,修复版 APK):

- 绑核日志:`大核判定: cpu_capacity, 各簇 rank = 313/777/1024` →
  `游戏主线程 -> 大核 [4,5,6,7]: 成功`
- FPS 序列:**95 → 105 → 110 → 114**(对比修复前同热态 1 fps、
  lmc 关 130 fps)——崩塌彻底消失,且随降温持续爬升

### 7.4 测试方法学教训(本轮踩坑全录)

| 坑 | 教训 |
|---|---|
| inactivityFpsLimit 写非法值静默回退 | MC 新选项必须用**合法枚举值**,上机前逐项核对 |
| 采样全在静置期 → 必触发 afk 降帧 | 基准机需把该项设 "minimized" |
| 不插电时 MIUI 全核压频(1.8GHz) | 基准必须插电,记录电量 |
| 热状态主导性能(轮间漂移 > 待测差异) | 冷却用**息屏**(亮屏地板 ~48°C);轮次交替抵消漂移 |
| 母本玩家生存模式会饿死/被打死 | 挂机基准用**创造模式**+满状态+正午冻结 |
| uiautomator 在游戏画面 null root(MIUI) | 采样改截图+多模态读数 |
| 贴脸墙景 = GPU 零负载,只测 CPU 侧 | 场景要有真实地形/树叶(alpha overdraw) |


## 八、柠枺实测:探图帧率崩塌与绑核策略调整(2026-10-14 晚)

### 8.1 柠枺 1.5 小时游玩观测(被动截图 167 样本,全程 lmc 开)

| 场景 | FPS |
|---|---|
| 静止/已加载区域 | 105~200 |
| 天空视角 | 240~490 |
| **飞行/探图(连续区块生成)** | **17~18,持续 30+ 分钟** |

柠枺的主观结论(探图比原版低约 30 帧、更不稳定)与数据吻合:
探图模式在 lmc 开启下长时间趴在 17-18 fps。

### 8.2 归因与策略调整

绑核使 Client 线程常驻性能核,飞行时区块生成(Server/Worker 线程)
被调度器挤到小核,渲染等不到网格 → 帧率趴死。静态场景绑核收益
(+5%)远小于探图损失(-90%)。

**调整**:主线程绑核改为**默认关闭**,`lmc_bind` 标记文件选用;
JVM 家务线程迁小核保留(良性)。绑核不再是默认行为,待有
"整体迁移策略"(Client+Server+Worker 同簇)的设计后再评估重启。
